# 子 Agent 分工與驗證教學 v1.0

日期：2026-09-05
狀態：依目前 Codex 官方文件整理的教學補強規格；尚未製作網站內容、未啟動示範 Agent、未做端到端驗證。

## 1. 必須先教清楚的差別

| 項目 | 它負責什麼 | 教學中的例子 |
| --- | --- | --- |
| 主 Agent | 理解總目標、切分工作、整合結果並向使用者負責 | 收集各子 Agent 結果，處理衝突後給出一份結論 |
| 子 Agent | 接受一項界線清楚、可獨立進行的任務 | 一位查現有程式、一位檢查測試缺口、一位核對文件 |
| Skill | 告訴 Agent 一套可重複使用的方法 | `grill-me` 規定需求訪談一次問一題 |
| MCP／外部工具 | 讓 Agent 連接資料或執行特定操作 | 查官方文件、讀設計系統或連接專案服務 |
| AGENTS.md | 提供整個專案長期遵守的規則 | 修改前先確認範圍、未測項目標記待確認 |

Skill 可以交給主 Agent 或子 Agent 使用；子 Agent 不是另一個 Skill。多開 Agent 也不代表結果自動正確，主 Agent仍需整合與驗證。

## 2. 何時適合使用

優先用於彼此獨立、可以同時完成的讀取型工作：

- 探索不同模組、整理不同來源、核對規格與程式。
- 一位執行測試、一位檢查操作流程、一位找回歸風險。
- 大量頁面或文件分區盤點，最後由主 Agent 統一規則與結論。
- 完成實作後，交給沒有參與修改的 Reviewer 做獨立檢查。

不適合直接使用的情境：

- 需求仍模糊，需要和使用者一問一答確認。
- 多項工作會同時修改同一文件、同一畫面或同一資料結構。
- 工作很小，協調成本比單 Agent 更高。
- 需要付款、發布、刪除、外部傳訊或正式資料寫入；子 Agent 不會產生額外授權。

官方文件也建議先把平行 Agent 用於探索、測試、分流及摘要；多 Agent 會增加 Token 用量，平行寫檔則容易產生衝突。

## 3. 新手可照做的啟動方式

在 Codex App、CLI 或 IDE 對主 Agent 直接說明要使用子 Agent，並交代分工、完成條件、是否等待全部結果，以及如何整合。

```text
請使用 3 個子 Agent 平行檢查這個專案：
1. Explorer：只讀取並整理目前頁面與資料流，不改檔。
2. Tester：執行現有測試，列出失敗與未涵蓋情境，不改檔。
3. Reviewer：依 PRD 檢查功能缺漏與回歸風險，不改檔。

請等待三個 Agent 都完成，再由主 Agent 合併結果。
若結論衝突，列出證據與待確認事項，不自行選擇產品規則。
```

Codex CLI 可用 `/agent` 查看及切換 Agent 執行緒。App 與 IDE 依目前介面查看子 Agent 狀態；實際按鈕與位置需以製作教材時的版本擷取。若工具沒有子 Agent 功能，就改成主 Agent 依序完成同一份工作，不假裝已平行執行。

## 4. 任務交付格式

每個子 Agent 的任務都要包含：

1. 目標：只交付一個可驗收結果。
2. 範圍：可以讀或修改哪些區域；預設先用唯讀任務示範。
3. 已知資料：PRD、版本、頁面、測試與專案規則。
4. 禁止事項：不可自行擴張功能、發布、刪除或處理正式資料。
5. 證據：檔案、頁面、測試輸出或官方來源。
6. 回傳格式：發現、風險、待確認、建議下一步。
7. 主 Agent 工作：等待所有結果、去重、處理衝突並重新驗證重要結論。

## 5. 00–10 教學搭配

| 階段 | 子 Agent 用法 | 角色／Skill 搭配 | 驗收界線 |
| --- | --- | --- | --- |
| 00 開發準備 | 先示範單 Agent；進階區說明如何檢查是否支援子 Agent | Explorer 唯讀核對工作目錄；主 Agent 維持總責 | 尚未開始開發，不讓多 Agent 同時改檔 |
| 01 需求訪談 | 不平行訪談，避免不同 Agent 同時追問造成規則分裂 | 主 Agent＋`grill-me` | 一次一題，由使用者確認需求 |
| 02 功能清單 | 可讓一位查需求遺漏、一位找重複，再由主 Agent整合 | 兩個 Reviewer 型唯讀 Agent | 不由子 Agent決定 P0 或新增功能 |
| 03 PRD | 可分正常流程、異常情境、非功能需求三個檢查面向 | 分析 Agent＋主 Agent統一產品規則 | 子 Agent提出缺口，產品決策仍回到使用者 |
| 04 原型 | 可分頁面盤點、互動狀態、行動版流程檢查 | Explorer／UX Reviewer；按需使用原型 Skill | 多個 Agent不並行修改同一份原型 |
| 05 UI 設計 | 可分視覺一致、可近用性、響應式檢查 | UI Reviewer、Accessibility Reviewer；設計 Skill 由主 Agent指定 | 先產生一個設計方向，再分工審查，避免各畫一套風格 |
| 06 TRD | 可分資料流、安全、API／保存方式檢查 | 架構 Reviewer＋安全 Reviewer | 主 Agent統一介面與資料定義 |
| 07 開發計畫 | 可請 Explorer 分析依賴，主 Agent排出唯一計畫 | Explorer 讀取程式與文件 | 不能由不同 Agent各自排一份互相衝突的主計畫 |
| 08 開發與測試 | 先按檔案責任分開；一位實作、一位測試或審查 | Worker 有清楚檔案所有權；Tester／Reviewer 盡量唯讀 | 同檔不可平行寫；主 Agent合併後重跑測試 |
| 09 驗收與版本 | 適合獨立的功能、資料、畫面、回歸檢查 | Tester、UI Reviewer、Code Reviewer | 各自結果只是證據來源，由主 Agent形成驗收結論 |
| 10 使用與發布 | 可讓 Agent檢查發布清單與公開資料；實際發布仍由主 Agent依授權處理 | Release Reviewer／Security Reviewer | 不把委派視為部署、付款或公開授權 |

## 6. 自訂 Agent 是進階內容

Codex 內建 `default`、`worker`、`explorer` 等角色，也可在個人或專案 `.codex/agents/` 建立 TOML 設定，定義名稱、用途、指令、模型及唯讀權限。第一版教材只教使用現有 Agent；建立自訂 Agent 放在進階章，不要求新手先修改設定。

需要建立自訂 Agent 時，先回答：這個角色是否會重複使用、是否需要固定 Skill／工具、是否應限制為唯讀、輸入與回傳格式是否已穩定。若只是一次任務，直接寫清楚委派提示即可。

- D-AG02：單 Agent／子 Agent 選路圖，依任務能否獨立、是否會改同檔、是否涉及外部操作判斷。

- S-AG02：CLI `/agent` 檢視流程；只在實際 CLI 版本驗證後加入。
- S-AG03：成功案例與失敗案例：清楚分工／重複工作、唯讀審查／同檔衝突、證據整合／直接照單全收。

驗收分開記錄：功能可用、Agent成功啟動、每個任務完成、主 Agent等待並整合、重要結果重新驗證、Token／時間差異。只看到多個執行緒不代表工作完成。
